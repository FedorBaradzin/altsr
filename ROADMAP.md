# ALTSR — Дорожная карта, как работает проект и что нужно

Дата: 2026-11-09. Статус: Фазы 0–4 реализованы и покрыты тестами (81 тест). Есть дизайн
платформы (Design-канвас) и моушн-интро (отдельные артефакты).

> ⚠️ Не инвест-рекомендация, не финсовет. Платформа про **скрининг и симуляцию**, а не
> про обещание прибыли. ~98% новых токенов обнуляются. Анти-скам снижает риск **кражи**,
> а не риск обнуления. Любое живое исполнение — под фиче-флагом, OFF по умолчанию.

---

## 1. Что это и в одном предложении
Платформа раннего обнаружения новых токенов, которая **сначала анализирует** (источники →
анти-скам → токеномика → сигнал), затем **симулирует** вход/выход на бумаге, и лишь после
длинного честного paper-трека допускает опциональное живое исполнение с жёсткими лимитами.

## 2. Как работает — сквозной конвейер
```
                   ┌─────────── ИИ-слой (новости, sentiment, LLM-оценка шортлиста) ───────────┐
                   ▼                                                                           │
discovery → safety_screen → signal_engine → executor(paper | live-flag) → notifier → dashboard
   │             │                │                    │                        │
 L1 on-chain  GoPlus/RugCheck  фильтры входа       цепочка выходов          Telegram/email
 +официальн.  honeypot.is      + volume-spike      TP/SL/trailing/stall     + web push
```
Каждый слой идемпотентен и переживает рестарт (состояние в БД, не в памяти).

**Стадии:**
1. **discovery** _(готово, Фаза 0)_ — GeckoTerminal new_pools (EVM+Solana), RugCheck new_tokens,
   DexScreener profiles → нормализация в единую модель Token → дедуп (Redis + UNIQUE в БД) →
   PostgreSQL → REST + WebSocket лента. Планово: on-chain WS-discovery по событиям фабрик DEX
   (`PairCreated`/`PoolCreated`) и Solana geyser/logs для минимальной задержки.
2. **safety_screen** _(готово, Фаза 1)_ — EVM: GoPlus + honeypot.is; Solana: GoPlus + RugCheck →
   `risk_score` 0–100 + `red_flags[]` + вердикт **PASS/REVIEW/BLOCK**. HARD-BLOCK: honeypot,
   sell_tax>15%, mint authority, владелец меняет балансы, топ-1>50%, LP не залочен, rugged.
   «Нет данных» → не PASS. Отдельный воркер пишет `safety_reports`.
3. **signal_engine** _(готово, Фаза 2)_ — ворота входа fail-fast (safety PASS → risk ≤ порог →
   ликвидность ≥ мин → возраст в окне → холдеры) → **BUY-сигнал** с причинами и уверенностью.
   Для каждого сигнала — блок **«где и как купить»** (swap-ссылки Jupiter/Uniswap/PancakeSwap,
   DexScreener/GeckoTerminal, эксплорер) + **Telegram-алерт**. Планово: добавить volume-spike
   (≥3x/≥2x), преобладание buy и лог точности. `/api/signals`, `/api/tokens/{id}/venues`.
4. **paper_executor** _(готово, Фаза 3)_ — по BUY-сигналу открывается **бумажная** позиция +
   **цепочка выходов по приоритету**: hard stop-loss → trailing от пика (после арминга +X%) →
   take-profit (частичный) → stall → time exit. Дневной лимит убытка, лимит позиций,
   прайс-фид DexScreener, издержки круга в P&L. Честная сводка (equity, return %, win-rate,
   avg win/loss) + **прогноз-план** (что бот сделает, НЕ прогноз прибыли). `/api/paper/*`.
   Планово (Фаза 5 live): перед каждой покупкой honeypot-симуляция, DCA, auto-blacklist.
5. **notifier / dashboard** _(частично)_ — Telegram/email/web push на PASS-сигналы, закрытия,
   критические события; дашборд с лентой, риск-карточкой, бумажными сделками и честной
   сводкой P&L (win-rate, avg R, max drawdown, net после издержек).

## 3. Фазы и критерии приёмки
| Фаза | Содержание | Статус |
|---|---|---|
| **0** | Лента новых токенов → дедуп → БД → экран | ✅ готово (15 тестов) |
| **1** | safety_screen: score + red_flags + PASS/REVIEW/BLOCK, HARD-BLOCK | ✅ готово (20 тестов) |
| **2** | signal_engine: BUY-сигналы + «где купить» + Telegram | ✅ готово (19 тестов) |
| **3** | paper_executor: TP/SL/trailing/stall, дневные лимиты, честный P&L | ✅ готово (17 тестов) |
| **4** | ИИ-слой: прогон новостей, классификация катализаторов (LLM + фолбэк) | ✅ ядро готово (10 тестов) |
| **5** | live-исполнение (OFF, фиче-флаг): Jupiter/0x/1inch, симуляция tx, подтверждение | ⬜ только после длинного paper-трека |

## 4. ИИ-слой: анализ и прогон новостей (как встроим)
Честно о «ежесекундном ИИ»: вызывать LLM на каждый токен каждую секунду **нереалистично** по
цене и задержке (тысячи токенов/час × стоимость токена-генерации × латентность). Рабочая
архитектура — **двухскоростная**:

- **Быстрый детерминированный путь (на каждый тик, без LLM):** всё, что уже есть — discovery,
  safety-правила, числовые сигналы (ликвидность, объём, buy/sell-поток, концентрация). Это
  несёт основную нагрузку «ежесекундно» и стоит почти ничего.
- **Медленный ИИ-путь (на шортлист и события, с кешем):** LLM запускается только для токенов,
  прошедших PASS и попавших в watchlist, или при событии (новость, резкий объём, разблокировка).
  Это десятки вызовов в минуту, а не тысячи.

**Что делает ИИ-слой (Фаза 4):**
1. **Ingestion новостей/соцсетей** — источники: X/Twitter (API), крипто-новости (RSS/News API),
   Bitcointalk ANN RSS, официальные блоги/Discord/Telegram проектов. Поток складываем в БД с
   привязкой к токену (chain+address) и временем.
2. **LLM-классификация новости** → структурированный выход: тип катализатора (листинг, партнёрство,
   аудит, эксплойт, разблокировка, делистинг), тональность (−1..+1), срочность, и статус
   достоверности (VERIFIED / OFFICIALLY ANNOUNCED / THIRD-PARTY REPORTED / UNVERIFIED /
   CONTRADICTED — из мастер-промта). Факты, оценки и гипотезы разделяются явно.
3. **LLM-оценка шортлиста** — краткий research-отчёт по токену (что делает проект, токеномика,
   риски контракта, разблокировки, позитив/негатив, неподтверждённые утверждения) + вклад в
   рейтинг как **отдельный** фактор с порогом уверенности. LLM **не может** перебить HARD-BLOCK
   безопасности (нельзя компенсировать критическую уязвимость маркетинговым рейтингом).
4. **Событийные алерты** — новость high-urgency по токену в позиции → сигнал executor'у
   пересмотреть выход (напр. эксплойт/делистинг → немедленный выход как критическое событие).

**Технически:** отдельный `ai_worker` + таблицы `news_items`, `ai_assessments`. Кеш ответов по
(контент-хэш, модель). Контроль затрат: лимит вызовов/мин, только шортлист, батчинг,
дешёвая модель для классификации + мощная для глубокого отчёта. Все LLM-выходы — строгий JSON
(structured output), с проверкой схемы; при провале — fallback на детерминированный путь.
LLM-выводы помечаются как «оценка», не «факт», и всегда со ссылками на источники.

## 5. Что нужно для этого
**Инфраструктура (уже в репо):** Docker Compose — PostgreSQL, Redis, backend (FastAPI),
воркеры (discovery, screener; далее signal, executor, ai), frontend (Next.js), GitHub Actions CI.
Деплой на VPS. Все ключи в `.env`/secrets, не в коде.

**API-ключи и сервисы (детальный каталог — в `research-landscape-and-autotrade-design.md`),
порядок «сначала первоисточники»:**
- L1 первоисточники: Solana RPC/Helius, EVM RPC, Etherscan/Basescan/BscScan, Solscan, GitHub token.
- L2 безопасность: GoPlus, RugCheck, honeypot.is (без ключа, но с rate-limit).
- L3 рынок/discovery: GeckoTerminal/CoinGecko Onchain, DexScreener, Birdeye (ключ).
- L4 фундаментал/новости: DefiLlama, Tokenomist, RootData, CryptoRank/ICO Drops, X/News API.
- ИИ: ключ LLM-провайдера (классификация + глубокий отчёт).
- Уведомления: Telegram Bot token, SMTP/почта (опц.), web push ключи (опц.).
- Для Фазы 5 (live, позже): отдельный кошелёк, приватный RPC, Jupiter/0x/1inch, бюджетные лимиты.

**Операционное:** мониторинг и журнал ошибок, rate-limit/ретраи/кеш (частично есть),
бэкапы БД, алерты на падения воркеров. Бюджет на API (LLM и платные дата-ключи) —
оценивается по объёму шортлиста и частоте новостей.

## 6. Риски и честные рамки (закодированы в UI/дисклеймерах)
- Детекция ловит ЧАСТЬ схем; slow-rug и новые паттерны проскакивают. PASS ≠ «безопасно».
- Анти-скам снижает риск кражи, а не обнуления. «Не скам» ≠ «вырастет».
- «Выход при малейшем падении» в наивном виде убыточен на издержках — используем trailing от
  пика с армингом и cost_floor (разбор в research-доке, раздел 4).
- Живое исполнение только после длинного paper-трека, под флагом, с симуляцией tx и
  подтверждением/дневным лимитом. По умолчанию — только бумага.

## 7. Ближайший шаг
Ядро всех пяти слоёв (discovery → safety → signal → paper → ИИ-новости) собрано и
протестировано; есть дизайн и моушн. Дальше — усиление: привязка новостей к токенам и
событийные алерты (эксплойт/делистинг по токену в позиции → немедленный выход); LLM-оценка
шортлиста как отдельный фактор; volume-spike/buy-pressure в signal_engine; календарь TGE
(pre-launch discovery). Live-исполнение (Фаза 5) — только после длинного paper-трека, под
фиче-флагом с симуляцией tx и подтверждением.
